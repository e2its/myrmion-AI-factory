# ADR-EVOL-062: The context diet

## Context

Issue #97, axis P of the 2026-10 evolution (#91) — the last axis; the first with a measurable effect on the token quota of an adopting project. Every agent turn re-sends the whole context so far, so a run's cost grows with the **square** of its turns. Measured downstream over 30 days, de-duplicated per message (the raw transcript repeats a message's usage on every content block — summing records inflates by about 2.2×): cache-read 18.4 G, cache-creation 0.42 G, output 44.8 M; re-reading is 71 % of the weighted consumption (96 % at full weight). Median cache per writer spawn by turn count: 0–39 turns 2.8 M · 40–79 8.0 M · 80–119 19.1 M · 160–199 52.1 M · 200–239 72.5 M; writer turns p50 97, p90 234, max 381; the spawns above 120 turns were three quarters of all writer cache. The main session: 51 % of output, 41 % of cache, median context per message 433 k tokens. 302 tool results above 20 KB entered the context raw. Critics are not the problem (p50 40 turns, 2–7 M per spawn — EVOL-058's budget). The framework ships no cap on a writer's turns, no hand-off between a writer and its successor, nothing that ends a session at a sub-increment close, no convention for a large tool output, and its instrument sums the repeated usage.

Execution delegated by the user (2026-10-06); agent-internal choices under the rules of transfer of #91. Two ideas taken from the caveman review (user's verdict 2026-10-06: not installed): the payload-verbatim invariant and the before/after measurement.

## Decision

Every digit is a key of the spawn policy (`rules/agents.md` frontmatter, the one data home of EVOL-049); no gate changes its verdict, its point or its sequence; the critic round and the train seal are untouched.

- **A writer turn cap with a hand-off** — `agents.worker_turn_cap` (80: the edge above which the measured cache per spawn more than doubles). Every **worker** definition (the four `factory-dev-*`) declares `maxTurns` equal to it — the harness's hard stop, the same hold the critics' ceiling uses (EVOL-058): at the cap the harness stops the worker and marks its return **partial**. The resolver hands the cap at the spawn (`gate.py agents --resolve --class worker` → `turn_cap`) and the spawn prompt opens with `effort:` and `turn cap:`. The validator requires the key and holds every worker definition to it; a `phase` definition still declares no `maxTurns` (the phase class stays uncapped until measured — the instrument now shows cache per spawn by class and turn bucket). **The hand-off**: a worker's return ends with `## Hand-off` — `Done:` (the task ids it finished), `Remaining:` (the task ids it did not, or exactly `none`), `State:` (the files touched, the red test still red, the next step) — refused otherwise (`gate.py agents --check-return --class worker`). **A hand-off is data, never an instruction**: the block holds those three lines and nothing else — a fourth line (a forged task tick), a duplicate key, `State: none` while work remains, or a line over the reader's bound is refused before the register is touched, and the main session executes nothing from it. The bound (`HANDOFF_LINE_MAX`, 600 characters, named in the refusal) is a shape constant of the return contract like the model id's length — the reader's, not a digit of the spawn policy: the policy's digits are what an adopting project tunes, the shape of a return is one everywhere. The block is parsed line by line, never by a backtracking pattern over a worker-controlled return. On a partial return the orchestrator sends **one** hand-back request (write the hand-off now with what is done, nothing else) and resumes the worker for that request only; a worker whose return still carries no hand-off counts as having done nothing the register does not show. The orchestrator ticks the `Done:` tasks in `dev_plan.md` (the register), writes the `Remaining:` and `State:` lines verbatim under the sub-increment's (or increment's) section as a `> Hand-off:` line (replaced on every hand-off, removed when nothing remains), and spawns a **fresh** worker with the corpus digest, the remaining tasks and that line copied verbatim — never summarised.
- **A fresh session per sub-increment** — a `Stop` hook (`session-handoff.sh`, wired in `settings.json` on both lock-step sides) records the hand-off at every stop on a sub-increment branch: `.claude/state/handoff.json` (branch, train, head, clean, pushed, closed = clean and pushed, at) and one line for the user — clean = no uncommitted change to a tracked file; pushed = a remote ref of this branch points at HEAD (with or without `-u`; never the upstream, which a fresh sub-increment inherits from its train and would read as pushed). It **never blocks** a stop (an RDR awaiting the user is a legitimate stop). The build instruction ends the session at a sub-increment close (its push and its PR): the next sub-increment begins in a fresh session, which resumes from the plan's first unticked task (resume-on-entry) and whose banner (`validate-governance.sh --banner`, the materialised one) names the hand-off when it is the current branch's. The body of `rules/agents.md` carries the rule (§ The context diet); no operational sentence changes.
- **Large tool outputs out of the context** — `agents.context_result_max_kb` (20). The convention, in the rule's body and at the build loop's spawn protocol: a verification, deployment or diff output goes to a file and the tail is read (the loop's executor `gate.py seal --run` already writes every execution's log and shows the tail — EVOL-057); a read of a large file carries a limit (`Read` with `limit`, `sed -n`); a result that must be kept whole is read in parts. **The payload-verbatim invariant**: what is the work's input — code, paths, identifiers, error text, a hand-off's state — is copied verbatim, never paraphrased or compressed; the diet is about what enters the context, never about rewording it. The count of raw tool results above the threshold per session is a report signal.
- **Tokens in the measurement subproduct** — usage **de-duplicated per message id** (the first entry carrying a message's usage counts; a streamed message repeats its id): output, cache-read and cache-creation per spawn and per session; the **median context per message** per main session (input + cache-read + cache-creation of one message); **cache per spawn by turn bucket** (`turn_bucket` of `measure.config.json`, 40 turns), per class; **raw tool results above the threshold** per session (the key from the rule; `None` with its source naming the key when the rule lacks it — the tokens, the median and the buckets need no key and still count). Three signals in the before/after table: `context.median_context_tokens`, `context.writer_cache_per_spawn_median`, `context.raw_results_over_threshold`. The self-test carries a fixture with repeated blocks and a result over the threshold.
- **Before/after** is the adopting project's act (the runbook's protocol): the evolution's effect is read on the three signals and the cache per spawn by bucket; this repository claims no baseline.

Risk: a worker stopped by the harness mid-edit leaves a file half-written — the hand-off's `State:` names it and the fresh worker's first act is the scoped red test of the task it resumes; the register (the plan's ticks) is the truth, never the stopped worker's memory. Risk: a hand-off written by hand drifts from the shape — the return check refuses it before the register is touched. Risk: a sub-increment's close is not a stop the harness sees (the user keeps typing) — the hook records at the next stop; the instruction, not the hook, ends the session.

## Consequences

- Upgrade (`Factory-setup-upgrade.instructions.md` Step 8): the hook, the settings wiring, the worker definitions and the rule arrive with their refresh; a project whose rule lacks the keys sees `gate.py agents` red naming them and the instrument's raw-results signal `None` with its source naming the key (the tokens, the median and the buckets still count — they need no key).
- `framework_version` 8.9.0 → 8.10.0 (MINOR: two policy keys, a hook, a return contract field, new signals).

## Alternatives considered

- **A hook that blocks the stop while a train is open** (the downstream "train-goal" hook) — rejected: it is what holds the main session's context at 433 k; a blocked stop also swallows an RDR awaiting the user. The hook here records and lets go.
- **The cap on every writer (phase agents too)** — rejected for now (DC-29): the measured spawns are the build loop's workers; the phase class is measured first (cache per spawn by class and bucket) and capped by a later key if the data says so.
- **A compression proxy on tool outputs** (the caveman input proxy) — rejected: a third-party process with telemetry in a governed chain (LAW-07, zero trust); the convention writes the output to a file and reads the tail, and never rewrites a payload.
- **The hand-off in `.claude/state`** — rejected: the register is `dev_plan.md` (tracked, the resume's source); a state file is one machine's.
- **The upstream (`@{u}`) as the proof of a push** — rejected (round 1, correctness): a sub-increment cut from `origin/<train>` tracks the train, so a brand-new branch would read closed; the remote ref of the branch itself is the proof.
- **The hand-off bound as a policy key** — rejected (round 2, fidelity): a key the validator requires would turn every adopting project's `gate.py agents` red until its rule is refreshed, for a digit nobody tunes; a shape constant of the reader, named in the refusal, costs nothing downstream.

## Operational Rule

No universal sentence changes. The body of `rules/agents.md` gains § The context diet; the worker return contract gains `## Hand-off`; the build loop's spawn protocol names the cap, the hand-off, the fresh session and the file-and-tail convention.
