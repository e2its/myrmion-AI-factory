# ADR-EVOL-051: One full verification loop per change

## Context

Issue #60, axis J of the 2026-09 evolution (#50): verification time is test time. Observed in the reference implementation on one pull request, the full build-verification loop ran **three times** for one change — before the read-only critics, again after the cures, and a third time at the push because the review reports and the plan's status were written after the second run. Then, with that fixed, recording the critics' round and correcting two lines of text re-ran the whole loop: the seal was all-or-nothing, the push hook recognised documentation only when the whole branch was documentation, and "documentation" had two definitions (the push hook's allowlist and the surface plan's class — the latter still ran the security scanners). And in the same pull request two green loops and a critic round did not see what the push then refused: the loop audited the governance digest of the implementation plan only, the push audited every planning artefact of the feature, including a design the change never touched whose digest had fallen behind the corpus.

In this framework the same three defects are latent: `full_verification_gate` (factory-build-verification) runs once per completion gate and then the completion gate writes `bvl_result` and the status into `dev_plan.md` — a tracked write after the green; the push-gate preflight carries its own hard-coded documentation allowlist while `planning.docs_exempt` (EVOL-048) is a second definition; `review_verification_loop` runs the coverage command and `full_verification_gate` runs the test suite — the same suite twice in one loop; and the governance digest of `design.md` (`governance_digest_version`, BLUEPRINT § GCD) is validated only by IMPLEMENT's Step 0b fast-path, never by a gate, never at the push, never for the other planning artefacts. Nothing the push would refuse is found before the push, and nothing the push honours is content-addressed.

## Decision

- **One order, stated everywhere.** Per completed diff: the **static round** (every gate profile member that needs no build and no database — the light profile of EVOL-046 — plus the new `digests` member) and the workers' red-first scoped runs as the test evidence → the **critics** (one round, EVOL-049) → **the artefacts** (the review and security reports, the plan's ticks and its status) → **one full loop** on those bytes → the **commit** on its green. Cures are re-checked while working by their scoped gate (`gate.py seal --plan` names it), never by a full loop per cure. The completion gate writes the plan's status and its verification record **before** the loop and nothing tracked after it; the loop's outcome lives in the seal, an untracked state file, never in a tracked artefact.
- **A content-addressed seal the push honours.** `python3 scripts/gate.py seal` is the one reader. The seal (`verification.seal.dir`, default `.claude/state/`, one file per branch) records, per gate, the hash of the gate's **read-set** (the paths `verification.gates.<name>.reads` declares, hashed over the tree the commit carries: git blob ids of the files on disk — identical to the committed tree's when nothing moved) and the outcome; a full loop also records the whole-tree hash. `--check` (a light profile member at the push; at CI it reports n/a — the seal is local state honoured at the push, CI runs the loop in its own job) recomputes every read-set at `HEAD`: a gate whose read-set moved since its green is **owed**; without a seal the reference is the diff base's tree (a branch that moved no read-set owes nothing); a changed path no gate reads and no documentation class covers is **unmapped** and owes the **full loop** — fail closed, the design's answer to the "gate that stops firing on a source it reads" defect; the map is validated (`--validate`: the documentation class defined, every gate declares a non-empty read-set, a repo that owes no seal says where its loop runs).
- **The incremental seal, by construction.** After a green seal, a delta re-runs only the gates whose read-set it touched (`--plan` lists them, with one **execution** per distinct command: a suite that feeds coverage is executed once and its result feeds every gate declaring that command). Documentation paths are in no read-set unless a gate declares them, so a documentation-only delta owes nothing — and a documentation path a gate does declare owes that gate.
- **One definition of documentation.** `config/quality.json → documentation` (`paths`, root-anchored globs; `exclusions`, always code whatever the extension — workflows, the behavioural contracts) is read by every consumer through `python3 scripts/gate.py documentation`: the push-gate preflight's review-lane skip (`--changed --base`), the planning gate's exemption (`planning.docs_exempt` is retired; planning reads the one list) and the seal's classification. Whether a comment-only change inside a code file counts is not a class decision: it is a path in a read-set or it is not.
- **The loop checks what the push checks.** `python3 scripts/gate.py digests` audits the governance digest of every planning artefact the feature owns (`verification.digest_artefacts`, default `design.md` and `dev_plan.md` under `docs/spec/{ID}/` — the technical artefacts; the journey is business-pure, LAW-16, and carries no digest — judged when present): the artefact's `governance_digest_version` must equal the current governance fingerprint (the snapshot's `constitution_hash[:8]`, the GCRP identity BLUEPRINT writes and IMPLEMENT Step 0b reads) and its text must name every rule the corpus binds to the feature's surface (`gate.py applicable --paths` — the one resolver): a bound rule the artefact never mentions is an incomplete digest. The member runs in the static round before the critics and in the profile at push — one predicate, never a copy.

## Consequences

- A change pays the full loop once, on the committed bytes; a documentation-only delta after a green seal pays nothing but the static round; a cure pays its scoped gate.
- The push refuses what the loop would have refused, and only that: a moved read-set, an unmapped path, a stale or incomplete digest — each found first in the static round.
- `planning.docs_exempt` is retired (breaking for a project that edited it: SETUP --upgrade moves the list to `documentation.paths`); the preflight's allowlist is a call, not a list.
- The gate map, the documentation class, the digest artefacts and the seal location are project configuration (SETUP materialises defaults from the stack: sources, tests, config, workflows); a project without a map is fail-closed — every non-documentation delta owes the full loop until the map exists.
- The train-close and push profiles of EVOL-046 do not change: `seal` and `digests` join the light members.
- **The seal is a local claim.** Like the LAW-13 review marker, it is written by the loop that ran and honoured by the push; nothing re-runs the gates to verify it, CI does not run the loop (no template CI job does) and reports the member n/a with that reason; a push that bypasses the hook bypasses the loop; the project's own CI test job, when it has one, is the compensating control.

## Alternatives considered

- **Keep the all-or-nothing seal and shrink what invalidates it** (ignore documentation writes after the green): rejected — two definitions of documentation again, and a gate that reads documentation (a docs build) would silently lose its signal.
- **A seal per commit stored in the artefact (`bvl_result: <hash>`)**: rejected — a tracked write after the green is the defect; the seal is state, not artefact.
- **A path-to-gate map inferred from the tools** (strace, coverage of the runner): rejected — brittle per stack; the declared map plus the fail-closed unmapped rule is the design that rules out a gate stopping to fire.
- **Digest currency by fingerprint only**: rejected — the reference incident was a corpus item missing from an untouched artefact; the fingerprint alone does not see a rule added beside an unchanged constitution.

## Operational Rule

`[LAW-05]` body (`rules/testing.md`) gains the order and the seal: one full loop per change, on the bytes the commit carries, sealed and honoured at the push; the static round and the digests before the critics. No universal sentence changes.
